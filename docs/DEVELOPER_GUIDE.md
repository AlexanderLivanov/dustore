## 1. Что такое Dustore

Платформа для инди-игр: разработчик бесплатно публикует игру, игроки находят её в каталоге, команды собираются на геймджемах. Вокруг магазина выросла целая экосистема: консоль разработчика, экспертная оценка, поиск команды, лента, чаты, магазин ассетов, база знаний, мобильное приложение-PWA.

**Стек намеренно простой:**

| Что | Чем сделано |
|---|---|
| Бэкенд | PHP 8.2+ **без фреймворка**, доступ к БД через PDO |
| База | MySQL / MariaDB (на проде MySQL 8) |
| Веб-сервер | Apache + `mod_php`, красивые адреса — в `.htaccess` |
| Фронтенд | Чистые JS и CSS, **без сборщика** (никакого webpack/npm-билда для сайта) |
| Фоновые процессы | Node.js: рассылка push-уведомлений (`pwa/push-worker.js`), мессенджер MINI (`mini-server/`) |
| Файлы | S3-совместимое хранилище (билды игр, картинки) |
| Платежи | ЮKassa, Robokassa |
| Вход | Telegram-виджет, почта+пароль, passkey (в мобильной версии) |

Никакой магии: открываешь `.php`-файл — видишь и логику, и HTML. Это одновременно плюс (всё на виду) и минус (файлы большие, логика и вёрстка перемешаны).

## 3. Как устроен сайт

### 3.1. Путь запроса

1. Браузер просит `/g/205`.
2. Корневой `.htaccess` переписывает его в `game.php?name=205` (так же `/d/<тикер>` → `dev.php`, `/player/<ник>` → `player.php`, `/fid/post/<id>`, `/p/<код>`). Любой `/имя` без расширения превращается в `/имя.php` (или `.html`).
3. Страница (`game.php`) подключает `swad/config.php`, а затем шапку `swad/static/elements/header.php` — она проверяет, кто пользователь, и подключает общие стили/скрипты.
4. Страница достаёт данные из БД, рисует HTML и подключает подвал `footer.php`.

**Страница = PHP-файл.** Нет контроллеров-роутеров, нет шаблонизатора. Новая страница — это новый `.php` в корне или в папке раздела.

### 3.2. Страницы и эндпоинты

Есть два типа PHP-файлов:

- **Страницы** — отдают HTML (`index.php`, `explore.php`, `game.php`, `jams/vote.php` …).
- **Эндпоинты** — маленькие скрипты, которые вызывают через `fetch` и которые отвечают JSON или делают редирект (`swad/controllers/*.php`, `api/*.php`, `jams/api.php`, `*/api/*.php`).

Общая логика лежит в **библиотеках** (классы/функции, их подключают `require_once`): `swad/controllers/user.php`, `game.php`, `swad/fx/*`, `l4t/lib/*`, `swad/controllers/jams/phase_lib.php` и т.д. Чёткого разделения папок «страницы / эндпоинты / библиотеки» нет — различай по содержимому.

### 3.3. База данных

- Подключение — класс `Database` из `swad/config.php`: `$pdo = (new Database())->connect();`. Параметры (хост, логин, пароль) выбираются по домену: на локалке и на проде разные. Сами пароли лежат в `swad/pass.php` (его в git нет, см. раздел 5).
- Основная БД `dustore`. У L4T своя — `desl4t` (`connect('desl4t')`), у GDDB своя — `gddb`.
- **Дампа схемы в репозитории нет.** Таблицы создавались по мере развития. Новые таблицы мы создаём либо **миграцией** (`migrations/*.sql` + `tools/migrate.php`), либо **самоустановкой** — функция вида `ensure_..._table()` делает `CREATE TABLE IF NOT EXISTS` при первом обращении (примеры: `swad/controllers/game_builds_schema.php`, `swad/fx/schema.php`, `swad/controllers/jams/presence.php`). Оба способа безопасно запускать повторно.
- Главные таблицы: `users`, `studios`, `games`, `game_builds`, `library`, `wishlists`, `game_reviews`, `sprints` + `sprint_participants`, `sprint_teams`, `sprint_prizes`, `sprint_experts`, `jam_votes`, таблицы магазина ассетов, `push_subscriptions` + `push_outbox` (пуши), таблицы чатов и ленты (`fx_posts`, `fx_comments`, `fx_reactions` …).

### 3.4. Кто вошёл на сайт

- Основной способ — **Telegram Login Widget** (`swad/controllers/auth.php`) или **почта+пароль** (`email_auth.php`). После входа ставится кука `auth_token` — самодельный JWT на 3 дня (`swad/controllers/jwt.php`) — и заполняется сессия `$_SESSION['USERDATA']`.
- Проверять права в коде принято через класс `User` (`swad/controllers/user.php`): `checkAuth()`, роли, принадлежность студии.
- **Записывающие запросы защищаются CSRF-токеном**: `csrf_token()` на странице → заголовок `X-CSRF-Token` или поле `csrf` в запросе → `csrf_valid()` на сервере (`swad/controllers/csrf.php`). Делай так в каждом новом эндпоинте, который что-то меняет.
- Мобильная версия `/m/` имеет свой вход (в том числе passkey), но в итоге ставит ту же сессию и ту же куку.

### 3.5. Оформление

- `swad/css/header.css` и друг. — общий каркас; у каждого раздела свой css (`explore.css`, `gamepage.css`, `vote.css`, `l4t.css`…).
- Цвета и тема переключаются классом на `<body>`; в css темы — отдельными блоками (`body.moonlight-theme …`). Новый стиль пиши так, чтобы работал во всех темах.
- Эффект «наклона» кнопок и карточек — `swad/js/float3d.js` + `swad/css/float3d.css`. Силу эффекта крутят только переменные в `float3d.css`.

### 3.6. Файлы и платежи

- Билды, картинки, аватары грузятся в S3 (`swad/controllers/s3.php`, `s3_multipart.php`, `storage.php`). Большие файлы — кусками (multipart).
- Покупки игр: `finv2/create_payment_game.php` → ЮKassa → вебхук `finv2/game_webhook.php` → игра попадает в `library`. Ассеты: `assetstore/` (свой процесс покупки).

### 3.7. Фоновые вещи

- **Push-уведомления:** страница → `chat/push_subscribe.php` → очередь `push_outbox` → Node-воркер `pwa/push-worker.js` → браузер. Подробная инструкция запуска — в `README.md`.
- **Почтовые рассылки студий:** очередь `email_queue`, отправка пачками (`devs/broadcast_lib.php`, `devs/broadcast_mail.php`).
- **Service Worker:** `sw.js` в корне — кэш и пуши. При правке обязательно меняй версию кэша, иначе пользователи будут видеть старое.

## 5. Запуск у себя

Короткая версия для Windows (XAMPP). Полная инструкция для Linux — в `README.md`.

1. Поставь **XAMPP** (Apache + MySQL/MariaDB + PHP 8.2+) и **Composer**. Включи в Apache `mod_rewrite` и `AllowOverride All` для папки сайта.
2. Склонируй репозиторий в `C:\xampp\htdocs` и выполни `composer install` (ставит PHP-библиотеки в `vendor/`, в git их нет).
3. Создай `swad/pass.php` — файл с доступом к БД и ключами сервисов (он в `.gitignore`). Образец структуры есть в `README.md`, раздел «Секреты». Попроси актуальные значения у владельца проекта; для локалки хватит БД и пустых ключей S3/платежей.
4. Создай базу `dustore` и залей в неё данные. Схемы в репозитории нет, поэтому проще всего снять дамп с боевой базы — для этого есть скрипты:
   - `tools/pull-db.sh` — по SSH снимает дамп, заливает в локальную БД, **обезличивает** (`tools/anonymize.php`: подменяет почты, токены, хэши паролей) и применяет миграции;
   - настройки скрипта — `tools/pull-db.env` (копируется с примера, в git не попадает).
5. Применить миграции вручную: `php tools/migrate.php` (только из консоли). Список выполненных хранится в таблице `schema_migrations`.
6. Открой `http://localhost/`. Вход через Telegram локально работает только с отдельным локальным ботом (константа `LOCAL_BOT_TOKEN`); проще войти по почте.

Push-уведомления и мессенджер MINI для обычной работы **не нужны** — их поднимай, только если правишь именно их.

## 6. Как работать: рецепты

**Добавить страницу.** Создай `имя.php` в корне (или в папке раздела). Начни с `require_once 'swad/config.php'`, подключи шапку `swad/static/elements/header.php`, в конце — `footer.php`. Адрес `/имя` заработает сам. Нужен адрес с параметром в пути (`/x/<id>`) — добавь правило в корневой `.htaccess`.

**Добавить эндпоинт.** Положи файл рядом с темой (`swad/controllers/…` или `<раздел>/api/…`). Проверь вход, проверь CSRF, проверь, что у пользователя есть права на конкретный объект (владелец студии, организатор джема), отвечай JSON. Образец — `swad/controllers/jams/save_vote.php`.

**Поменять базу.** Новый столбец или таблица — файл `migrations/NNNN_название.sql` (только добавления, идемпотентные: `IF NOT EXISTS`). Либо самоустановка `ensure_*_table()` для таблиц, которые должны появляться сами. Никогда не удаляй и не переименовывай столбцы в одной миграции с кодом, который их ещё использует.

**Новый джем.** Итоги и номинации описываются в одном месте — `swad/controllers/jams/jam_awards.php` (`reveal_at`, `sprint_id`, список наград). Фазы джема считает `swad/controllers/jams/phase_lib.php`. Страница голосования — `jams/vote.php`.

**Поправить стили.** Найди css страницы по таблице в разделе 8 (папка `swad/css/`). Для каждой темы (moonlight, madness) смотри, нет ли отдельного блока. Для карточек/кнопок не переопределяй переменные `float3d.css`.

**Выложить на сервер.** Прод может отличаться от git: на нём лежат загруженные пользователями файлы и локальные правки. Поэтому не делай слепой `git pull` на проде. Выкладывай нужные файлы осознанно: сначала сравни версию на проде с тем, что собираешься залить; конфиги и секреты на проде не перезаписывай. Закончив — проверь на проде затронутую страницу и журнал ошибок Apache.

## 7. Правила и подводные камни

- **Секреты не коммитим.** Пароли БД, ключи S3, токены ботов, ключи платёжек — только в `swad/pass.php`, `.env` или переменных окружения. Если нужен новый ключ — добавь заглушку в пример (README), а не значение в код.
- **Каждый эндпоинт проверяет права на объект**, а не только факт входа: «залогинен» ≠ «может менять этот джем/студию/игру».
- **SQL — только через подготовленные запросы** (`prepare` + `execute` с параметрами). Склеивать строку из пользовательских данных нельзя.
- **Вывод в HTML — через экранирование** (`htmlspecialchars` / локальный хелпер `h()`).
- **Заголовки и cookie раньше вывода.** `setcookie`, `header()` и `session_start()` вызывай до любого `echo` и до подключения шапки, иначе «headers already sent». Это частая причина падений.
- **Время.** Часовой пояс сайта — Москва (`APP_TZ` в конфиге). В базе даты хранятся как есть; считая интервалы, сверяй, в каком поясе записано поле.
- **Файлы с пометкой `_old`, `.bak`, дубли** — наследие. Не правь их и не подключай заново; если уверен, что не нужны, удаляй отдельным коммитом.
- **Большие файлы** (`index.php`, `game.php`, `explore.php`) правь точечно: рядом много чужих блоков. После правки открой страницу в двух темах и на телефоне.
- **Мобильная версия** (`/m/`) — отдельная кодовая база с собственными стилями; правка десктопной страницы её не меняет.
- **Не коммить в репозиторий**: логи, дампы БД (`*.db`, `*.sql` с данными), `.idea/`, загрузки пользователей, бэкапы (`*.bak`).
- **Коммиты и ветки.** Работаем через ветку и Pull Request в `main`. Сообщение коммита — коротко и по-русски: что изменилось и зачем.

## 8. Справочник по файлам

Формат записи: `имя файла` — что это; затем 1–2 предложения: что внутри и когда сюда лезть. Пометка «устарел / кандидат на удаление» означает, что файл не используется — перед удалением проверь поиском по проекту.

Порядок: корень и мелкие папки → `swad/` → `swad/controllers/` → джемы → консоль разработчика, эксперты, платежи, ассеты → L4T, лента, чаты, GDDB → API, мобильная версия, К.О.Н.Т.У.Р. → MINI.

### Корень

В корне лежат публичные страницы сайта (каждая открывается как `/имя` без `.php` — это делает корневой `.htaccess`), конфиги проекта и несколько бинарников для скачивания. Общая логика (БД, сессии, шапка/подвал, контроллеры) живёт в `swad/`, корневые страницы её подключают через `require_once('swad/config.php')`.

**Конфиги, документы и служебное**

- `.htaccess` — главный файл маршрутизации Apache для всего сайта. Закрывает все «точечные» файлы и папки (`.env`, `.git`, `.idea`; `.well-known` оставлен для Let's Encrypt) ответом 404, делает короткие адреса (`/d/<тикер>` → `dev.php`, `/g/<id>` → `game.php`, `/player/<ник>` → `player.php`, `/fid/post/<id>` → `fid/index.php`, `/p/<код>` → `media/post.php`, `/jams/api` → `jams/api.php`), прячет расширения `.php`/`.html` и поднимает лимиты PHP (загрузка до 1 ГБ, 300 с, 512 МБ памяти). Ломать нельзя: от него зависят почти все URL; при добавлении нового красивого адреса правило пишется сюда.
- `.gitignore` — что не попадает в git: секреты (`swad/pass.php`, `.env`, `l4t/.env`, `tools/pull-db.env`), `vendor`, `node_modules`, `uploads`, пользовательский контент (`swad/usercontent`, `webplayerdata`), `.idea`, `newmagazine/`. Если «пропал» новый файл в git — проверь, не попал ли он под эти маски (например, `package.json` и `package-lock.json` в списке, но уже закоммичены).
- `.gitattributes` — принудительные окончания строк LF и пометка бинарных расширений (png, jpg, exe, ttf и т.д.). Нужен, чтобы редакторы на Windows не переписывали весь проект в CRLF.
- `composer.json` — PHP-зависимости: AWS SDK (S3-хранилище), Robokassa и ЮKassa SDK (платежи), PHPMailer (почта), web-push (push-уведомления), getID3 (теги аудио). Ставится командой `composer install`, результат — папка `vendor/` (не в git).
- `composer.lock` — зафиксированные точные версии пакетов из `composer.json`. Руками не правят; обновляется через `composer update`.
- `package.json` — зависимости Node.js (`express`, `mysql2`, `web-push`, `dotenv`) для вспомогательных Node-сервисов, в первую очередь `pwa/push-worker.js`. Сам PHP-сайт от Node не зависит; в `.gitignore` это имя тоже значится.
- `package-lock.json` — точные версии npm-пакетов к `package.json`. Руками не править.
- `manifest.json` — манифест PWA (установка сайта как приложения): название, цвет темы `#14041d`, иконки, ярлыки на `/games` и `/app`. Подключён на главной через `<link rel="manifest">` в `index.php`.
- `sw.js` — главный Service Worker сайта (v2.x), регистрируется из `index.php` и `pwa/push-client.js`. Кэширует страницы (сначала сеть), CSS/JS (stale-while-revalidate) и картинки (сначала кэш), не трогает API/POST/APK и содержит обработку Web Push для чата. При правке меняй версии `CACHE_*`, иначе у пользователей останется старый кэш; старый `/m/sw.js` теперь только «самоудаляется».
- `robots.txt` — правила для поисковиков: всё открыто, кроме `/swad/*` и `/devs/*`, указан sitemap.
- `sitemap.xml` — карта сайта из четырёх адресов (`/`, `/devs`, `/games`, `/login`), сгенерирована внешним сервисом. Сильно устарел — игры и студии в нём не перечислены.
- `LICENSE` — лицензия Apache-2.0 на весь код.
- `README.md` — описание проекта для GitHub: что умеет платформа, планы, стек, пошаговая инструкция «Своя копия Dustore» (XAMPP/Apache, `swad/pass.php`, запуск) и траблшутинг. Начинай знакомство с проектом отсюда; баннеры берёт из `.github/readme/`.
- `SECURITY.md` — политика безопасности: поддерживаются версии 1.13+, о найденных уязвимостях просят писать в Telegram `@dusty_manager`.
- `constants.php` — пустой файл (только `<?php`). Никем не подключается; остаток от прежних планов, можно не трогать.
- `source.json` — источник приложений в формате AltStore/SideStore (для iOS): описывает MessengerExample (`ios/MessengerExample.ipa`) и MINI (`MINI-unsigned.ipa`) со ссылками на скачивание. Если меняешь .ipa — обновляй версию и дату здесь.
- `subscriptions.json` — файл со списком Web Push подписок браузеров (endpoint и ключи подписчиков). Пишется скриптом `save-subscription.php`; внутри персональные ключи подписок, значений не копируем и не публикуем. Это старый механизм; новый пуш чата работает через БД (`push_outbox`) и `pwa/`.
- `save-subscription.php` — старый приёмник Web Push подписки (POST JSON): добавляет её в `subscriptions.json`, если такой ещё нет. Данные не проверяются и не привязаны к пользователю; новый код пушей опирается на `chat/` и `pwa/`.
- `proxy.php` — «мини-прокси»: принимает POST `url`, скачивает страницу через cURL и отдаёт текст. Нужен только `client.php`; экспериментальный файл, в новых задачах не используй, кандидат на удаление.
- `client.php` — тестовая страница «Mini Browser» с полем URL и iframe, которая гоняет адрес через `proxy.php`. Экспериментальный инструмент, посетителям не нужен.

**Публичные страницы сайта**

- `index.php` — главная `/`. Витрина: подборки игр, студий, баннеры (в том числе промо), регистрирует `sw.js` и подключает `manifest.json`; на мобильных через `swad/controllers/mobile_redirect.php` отправляет в `/m`. Использует таблицы `games`, `studios`, `users`. Самый большой файл корня (~115 КБ) — правь аккуратно.
- `explore.php` — каталог игр `/explore`. Постраничная подгрузка по 48 игр (`EXPLORE_PAGE`), фильтры по жанру, разделы `?adult=1` и `?web=1`, сортировка по популярности; запросы идут через `Game::queryGames()` из `swad/controllers/game.php`.
- `game.php` — страница игры; открывается как `/g/<id>` (в `.htaccess` превращается в `game?name=<id>`). Самая большая страница сайта (~93 КБ): описание, скриншоты, отзывы, покупка/скачивание, вишлист, веб-плеер, блок «над игрой работали». С флагом `?embed=1` рисуется без шапки/подвала — так её использует `library.php` внутри iframe. Зависит от `swad/controllers/game.php`, `deplex_web.php`, `trailer_embed.php`, `og.php`; таблицы `games`, `library`, `wishlists`, `users`, `studios`, `staff`, `sprints`.
- `dev.php` — страница студии `/d/<тикер>` (`dev?name=<тикер>`). Только оболочка: тело (баннер, девблог, команда, награды) рисует `FxPages::studio()` из `swad/fx/pages.php`, он же используется в мобильной версии `/m/dev/<тикер>`.
- `player.php` — профиль игрока `/player/<ник>` (`player?username=`). Тонкая оболочка над `FxPages::player()` из `swad/fx/pages.php` (стена, коллекция, друзья, отзывы, безопасность); тот же код зовёт мобильное PWA.
- `player_old.php` — устаревший дубль профиля игрока (ещё от 05.2025) с прямыми SQL-запросами к `users`, `library`, `game_reviews`, `friends`, `achievements`. Заменён `player.php` и движком `swad/fx`; на него ничего не ссылается, роутера под него нет.
- `profile.php` — «Моя коллекция» `/profile`: личная библиотека купленных/сохранённых игр и предметов текущего пользователя (без `?user_id` — чужие профили теперь только через `/player/<ник>`). Без входа редиректит на `/login`; таблицы `library`, `games`, `users`. На неё ссылаются страницы `l4t/` и мобильная версия.
- `profile_old.php` — устаревший дубль `profile.php`. Заменён новой версией, нигде не используется, кандидат на удаление — не возвращай его в работу.
- `library.php` — «Библиотека» `/library` в стиле Steam: слева список игр пользователя, справа сама страница игры `/g/<id>?embed=1` в iframe. Читает `library`, `games`, `wishlists`, `users`; новые поля игры добавляются только в `game.php` и появятся тут автоматически.
- `me.php` — адрес `/me` («Мой аккаунт»): теперь только перенаправляет залогиненного на `/player/<ник>` (а гостя на `/login`), а если ника ещё нет, показывает окно выбора ника. Адрес сохранён ради ссылок из старых уведомлений и закладок — не удаляй.
- `login.php` — вход и регистрация `/login`: Telegram-виджет (боты `dustore_auth_bot` на проде и локальный бот на dev-хосте), вход по почте через `swad/controllers/email_auth.php`. Уже авторизованного (cookie `auth_token`) отправляет на `?backUrl=` или на главную; на него ссылаются `conference.php`, `verify.php`, страницы `l4t/`.
- `logout.php` — выход `/logout`: уничтожает сессию и редиректит на `/`. Две строки; cookie `auth_token` не трогает.
- `reset.php` — сброс пароля `/reset?token=…`: показывает форму нового пароля и по POST меняет его в `users`, гася токен. Ссылку присылает `swad/controllers/email_auth.php`.
- `verify.php` — подтверждение почты `/verify?token=…`: ищет `users.verification_token`, ставит `email_verified` и показывает результат. Ссылка приходит в письме из `swad/controllers/email_auth.php` и `resend.php`.
- `unsubscribe.php` — отписка от почтовых рассылок `/unsubscribe?u=ID&t=ТОКЕН`: GET показывает кнопку (сразу не отписывает, чтобы почтовые сканеры не отписывали случайно), POST делает отписку (в том числе One-Click по RFC 8058) или возвращает подписку. Ссылки генерирует `devs/broadcast_lib.php`; пишет в `users`. Подпись в ссылке не ломай.
- `notifications.php` — центр уведомлений `/notifications` для залогиненного (иначе на `/login`): список и отметка «прочитано» через `swad/controllers/NotificationCenter.php`. Ссылку на него даёт шапка сайта.
- `search.php` — поиск `/search`: загружает студии и пользователей из `studios` и `users` и фильтрует их на клиенте. Выбирает всех подряд, поэтому на большой базе будет тяжёлым.
- `users.php` — список игроков `/users`: поиск по `?q=`, подгрузка по 40 (`USERS_PAGE`, режим `?ajax=1`); почту в выборку не берём намеренно. Читает `users`.
- `studios.php` — каталог студий `/studios`: карточки из таблицы `studios` (аватар, описание, сайт, тикер для ссылки `/d/<тикер>`).
- `stat.php` — публичная страница «Статистика Dustore» `/stat`: счётчики игр, пользователей, студий, скачиваний, оценок и график онлайна (`users_online_history`). Хелпер `qv()` не даёт странице упасть, если таблицы или колонки нет; на неё ссылаются главная и страницы `jams/`, `assetstore/`.
- `wallet.php` — «Мой баланс» `/wallet`: красивая заглушка с жёстко прописанными «0 ₽ / 0 Ⓓ», без работы с БД и платёжками. Реальные платежи сейчас в `checkout.php` и в `swad/`.
- `checkout.php` — корзина и оформление `/checkout`: читает корзину из cookie `USERCART`, достаёт игры через `Game::getGameById()`, считает итог; добавление/удаление идёт в `swad/controllers/cart_ajax.php`. Использует `swad/controllers/user.php` и `game.php`.
- `promo.php` — публичная страница о продвижении игр `/promo`: на неё ведёт кнопка «промо» с баннера на главной (`swad/static/elements/promo_banner.php`) и страница `devs/promotion.php`. Статичная, БД почти не трогает.
- `about.php` — «О платформе» `/about`: миссия, описание экосистемы, обычная верстка с общей шапкой и подвалом. Только текст.
- `launcher.php` — лендинг DustoreX `/launcher`: лаунчер каталога для Windows и Android (разработка студии eXepc) со своим тёмно-бирюзовым оформлением (стили под `.dxl`). Ведёт на `/downloads/DustoreX-Setup.exe` и `/downloads/DustoreX-Android.apk`, картинки берёт из `/swad/static/img/launcher/`, «что нового» — из `/whatsnew`. При выходе новой версии меняй номера в тексте и файлы в `downloads/`.
- `dplx.php` — лендинг утилиты deplex `/dplx` (в тексте страницы и в `devs_edit_deplex_tab.php` её называют `/deplex`): объясняет разработчикам заливку билдов командной строкой и отдаёт `/deplex/deplex.exe`. Статичная страница с шапкой и подвалом сайта.
- `webplayer.php` — веб-плеер браузерных игр `/webplayer?id=N`: качает zip игры (только с разрешённых хостов `WP_ALLOWED_HOSTS`), распаковывает в `webplayerdata/<id>/www/` и отдаёт игру во фрейме; режим `&status=1` возвращает JSON состояния. Есть лимиты размера (700 МБ zip, 2 ГБ распаковки, 20000 файлов), запрещённые расширения и очистка через 6 часов; на него ссылаются `game.php` и `m/lib.php`. Осторожно с безопасностью — тут работает с чужими архивами.
- `conference.php` — запись на слоты онлайн-конференции джема `/conference`: питчи команд и соло-участников. Хранит записи в JSON-файле `swad/data/conf_slots.json` под `flock`, личность и капитанство определяет только на сервере по `sprint_teams`/`sprint_participants`. Перед каждым новым джемом меняй константу `SPRINT_ID`; POST обрабатывается до подключения шапки.
- `feed.php` — старый прототип «Лента разработчиков» (`/feed`) на Quill и JS-массиве постов в памяти, без записи в БД. Заменён полноценной лентой `/fid` (папка `fid/`); в шапке сайта кнопка ведёт уже на `/fid`.

- `agreement.html` — текст пользовательского соглашения (`/agreement`, расширение прячет `.htaccess`).

### music

Мини-плеер и загрузчик музыки `/music`: загрузка файлов до 500 МБ с обложками, поиск, очередь, перемешивание.

- `player.js` — фронтенд плеера (~29 КБ): библиотека, очередь, кнопки play/prev/next/shuffle, поиск, загрузка файлов; общается с `index.php`.
- `style.css` — тёмная тема плеера, стили панелей библиотеки и очереди.

### pwa

Код Web Push и «PWA-обвязки» для чата: подписка браузера, обработка push в Service Worker и фоновая отправка. Подключается из `chat/index.php` и мобильных `/m/chat`, `/m/profile`.

- `push-client.js` — клиент в браузере: регистрирует `/sw.js`, подписывает устройство на Web Push, возвращает состояние (`on/off/denied/unsupported`) и отдаёт звук уведомлений. Публичный VAPID-ключ берёт из `window.VAPID_PUBLIC`; звать `initPush()` нужно из клика пользователя, иначе браузер не покажет запрос.
- `push-worker.js` — Node-процесс (`npm i web-push`, Node 18+), который читает очередь `push_outbox` через `/chat/push_outbox.php` и рассылает Web Push. VAPID-ключи и секрет моста берёт из окружения/файлов-конфигов (в самом файле значений нет); должен быть запущен отдельно на сервере (systemd/pm2).
- `sw-push.js` — готовые обработчики событий `push`, `notificationclick` для Service Worker. Служат образцом: фактически эти обработчики уже вмержены в корневой `sw.js`, так что отдельным SW этот файл регистрировать не надо (два SW с пересекающимся scope конфликтуют). Иконки `/pwa/icon-192.png` и `badge.png` в нём указаны как «свои», но в папке их нет.

### tools

Скрипты разработчика для локальной работы с базой; запускаются только из консоли. `.htaccess` внутри запрещает доступ из браузера (`Require all denied`).

- `.htaccess` — одна строка `Require all denied`, закрывает папку от веб-доступа. Не удалять.
- `migrate.php` — накатчик SQL-миграций: `php tools/migrate.php [--status] [--baseline]` применяет файлы `migrations/*.sql` по порядку имён и помечает их в таблице `schema_migrations`; `--baseline` отмечает всё как применённое без запуска (для прода, где изменения уже сделаны руками). Подключение — переменные окружения `DB_HOST/PORT/NAME/USER/PASS`; из браузера не работает (в вебе отвечает 404). Применённые миграции не редактируем — новое изменение = новый файл.

- `pull-db.sh` — bash-скрипт (Git Bash на Windows/XAMPP): по SSH снимает дамп прод-базы, заливает в локальную, затем запускает `anonymize.php` и `migrate.php`. Настройки (SSH-цель, имена БД, пути) читает из `tools/pull-db.env`, который в git не попадает; пароль БД лежит на сервере в `~/.my.cnf`.

### swad/

Что значит имя «swad» в коде нигде не расшифровано; README называет папку просто «ядро» (`config.php`, `controllers/`, `css/`, `js/`, `static/`). Читай так: общая часть сайта, которую используют почти все страницы. Страницы подключают её одной из двух строк: `require_once 'swad/static/elements/header.php'` (шапка, которая сама подтягивает `config.php`, стили и скрипты) или `require_once 'swad/fx/boot.php'` / `FxPage` (движок постов). `swad/controllers/` описан в другом разделе.

**Корень swad/**

- `.htaccess` — запрет прямого доступа. Закрывает всю папку (`Deny from all`), но разрешает localhost и запросы с путём `/swad/`. Из-за строки `SetEnvIf ... ^/swad/ internal` защита, по сути, ослаблена: css/js/картинки отдаются, а php лучше проверять отдельно.
- `config.php` — главный конфиг. Подключает `pass.php` (его нет в git, README: «Секреты: swad/pass.php»). Содержит константы `REGISTRATION_ENABLED` (открыта ли регистрация), `APP_TZ` (часовой пояс), `ONLINE_WINDOW_MIN` (сколько минут считается «онлайн») и класс `Database`. У класса есть `get_creds()` (выбирает параметры по `HTTP_HOST`: локально или на проде), `connect()` (PDO к MySQL, по умолчанию база `dustore`, кодировка utf8mb4 и часовой пояс) и обёртки `Select/Insert/Update/Remove/executeStatement`. Лезь сюда, если меняешь подключение к БД или часовой пояс. Значения здесь не приводим.

### swad/controllers/

Это «общий кухонный шкаф» сайта: сюда сложены и AJAX-эндпоинты (файл вызывают по URL `/swad/controllers/имя.php` через fetch/форму, он отвечает JSON или редиректом), и PHP-библиотеки (классы и функции, которые подключают через `require_once`), и несколько кусочков HTML-шаблонов. Чёткого разделения нет, различать надо по содержимому: если в файле `class`/`function` и нет `$_POST`/`header('Content-Type...')` — это библиотека; если читает `$_POST`/`$_GET` и сразу делает `echo json_encode` — эндпоинт. Файлы с `_` в начале — внутренние хелперы или временные диагностики. Подпапка `jams/` описана отдельно, подпапка `l4t/` — в группе «L4T» ниже. Почти все эндпоинты берут пользователя из `$_SESSION['USERDATA']`, БД — через `new Database()` из `swad/config.php`.

#### Авторизация, сессия, пользователь

- `user.php` — класс `User`, главный «пользовательский» класс сайта (~700 строк).
  Методы: `getID`, `getUsername`, роли и права (`getUserRole`, `userHasRole`, `checkRole`), `checkAuth`/`auth` (проверка JWT из cookie `auth_token`), организации студии (`addUserToOrganization`, `getUO`), смена username/пассфразы, библиотека игр и корзина (`updateUserItems`, `updateUserCart`, cookie `USERCART`), друзья. Таблицы: users, library, staff, studios, user_organization, roles, friends. Подключается почти везде (api/, chat/, assetstore/, devs/ ...). Сюда лезем при любой работе с пользователем и правами.
- `jwt.php` — библиотека: `generateToken`, `validateToken`, `authUser`.
  Свой самодельный HS256-JWT на секрете из `swad/pass.php`, живёт 3 дня, id внутри — telegram_id. Подключают auth.php, email_auth.php, ppauth.php, user.php, m/api/auth.php.
- `auth.php` — эндпоинт, GET `/swad/controllers/auth.php?hash=...` — вход через Telegram Login Widget.
  Проверяет подпись Telegram, создаёт/обновляет запись в `users`, ставит JWT-cookie и сессию, редиректит назад (по Referer). Вызывается из login.php (data-auth-url) и m/js/auth.js (мобильная версия).
- `email_auth.php` — эндпоинт (POST из login.php и m/api/auth.php): вход и регистрация по email+паролю.
  Внутри CSRF, rate-limit, антибот-поле `website`, хелперы `generateFakeTelegram`, `loadSessionUser`, `logBotAttempt`; письма подтверждения шлёт через `send_email.php`; редиректит на `backUrl`. Таблица users, JWT. Сюда лезем при проблемах с логином/регистрацией по почте.
- `ppauth.php` — библиотека `ppLogin($username,$passphrase)`: вход по «кодовой фразе».
  Проверяет пассфразу в таблице users и выдаёт JWT. Нигде в репозитории не вызывается — похоже на устаревшую/заброшенную фичу (с 2025 г.), перед удалением проверьте.
- `logout.php` — эндпоинт: чистит сессию и cookie, редирект на `/`. Вызывают expert/admin, m/views/profile.php, kontur и др.
- `account_security.php` — эндпоинт (POST fetch, CSRF), вкладка «Безопасность» профиля: `action=bind_email` (привязать почту+пароль) и `action=change_password`. Ответ всегда JSON `{ok,message|error}`. Таблица users. Вызывается из me.php и swad/fx/pages.php.
- `profile_update.php` — эндпоинт (POST fetch, CSRF в заголовке): сохраняет username, city, country, vk, website из окна «Изменить профиль». Отвечает JSON `{ok, username, profile_url}` или с ошибками по полям. Дергается из `swad/static/elements/profile_edit.php`.
- `csrf.php` — библиотека: `csrf_token()`, `csrf_field()`, `csrf_valid()` — один токен на сессию, сравнение через `hash_equals`. Общий хелпер для api/, assetstore/, devs/, L4T. Не путать с `email_auth.php`, у которого свой отдельный `csrf_token` в сессии.
- `get_user_activity.php` — библиотека-одиночка `getUserLastActivity($telegramId)` (читает `users.updated`). Используется только в устаревшем `player_old.php` — кандидат на удаление вместе с ним. Внутри `require_once 'swad/config.php'` с относительным путём, который работает не из любой папки.
- `roles.php`, `security.php` — пустые файлы (0 байт). Остатки старых планов; `security.php` где-то ещё упоминается в require (me.php, devs/includes/header.php, swad/fx/pages.php), поэтому не удаляйте, не проверив — но содержимого там нет, ничего не делает.

#### Джемы (спринты) — отдельные эндпоинты вне jams/

#### L4T (подпапка l4t/)

Сервис поиска команды (Looking for Team). Эндпоинты тут вызываются из страниц `/l4t/` и JS (`l4t/js/l4x*.js`); все пишущие запросы проверяют CSRF через `_csrf.php`. Данные заявок — в БД L4T (таблицы bids, responds, profiles).

- `l4t/upsert_bid.php` — эндпоинт POST (форма): создание и правка заявки «ищу людей/команду» (поля bid_id, owner_type, owner_id, jam_id, pay_type, skills...). Проверяет, что студия принадлежит пользователю; сохраняет навыки; редиректит на `/l4t/?tab=...`. Зовут l4t/index.php и l4t/lib/market.php.
- `l4t/respond_bid.php` — эндпоинт POST JSON: отклик на заявку (таблица `responds`, счётчик в `bids` в транзакции; нельзя откликнуться на свою). Зовёт l4t/js/l4x.js и l4x-market.js.
- `l4t/l4t_update.php` — эндпоинт POST JSON: сохранение блоков профиля L4T по полю `type` (в т.ч. `exp`, `role`; таблица `profiles`, часть — в `users`, картинки в S3). Зовёт l4t/js/l4x.js.

- `_check_replies.php` — временная диагностика: GET `?game_id=` печатает текстом (text/plain) отзывы игры, ответы студий и отзывы ассетов. Доступ только root (`global_role = -1`), иначе 403. Сам в шапке говорит «удалить после проверки» — в проде не нужен, никем не вызывается.
- `_check_time.php` — временная диагностика часовых поясов: печатает текстом данные `users` и `users_online_history` (разница времени сервера/БД, окно «онлайн»), только для root. В проде не нужен, никем не вызывается, удалить.

### jams/

Папка `jams/` — это страницы системы геймджемов (в коде и БД джем = «спринт», таблица `sprints`): список джемов, страница участника, админка, голосование, статистика и публичный API. Вся серверная «логика кнопок» (регистрация, команды, загрузка билдов, приём голосов) живёт не здесь, а в `swad/controllers/jams/` (см. вторую часть). Красивых URL нет почти нигде: страницы открываются как `/jams/<файл>.php`, только `/jams/api` переписан в `.htaccess` (`^jams/api/?$` -> `/jams/api.php`). Часть ссылок в коде пишут без `.php` (`/jams/vote?id=12`) — это работает через настройки Apache.

Жизненный цикл джема (только то, что подтверждено кодом):

1. Создание: форма на `/jams` шлёт запрос в `swad/controllers/create_sprint.php` (это вне папки `jams/`; создаёт строку в `sprints`). Редактирование настроек и дат — `jams/admin.php` -> `swad/controllers/update_sprint_settings.php`. Даты в `sprints`: `registration_start/end`, `jam_start/end`, `voting_start/end`, плюс `expert_voting_end` (продлённое окно для жюри).
2. Регистрация и команды: `join_sprint.php` пишет в `sprint_participants`; команды — `create_team`, `invite_member`, `respond_invite`, `leave_team` (таблицы `sprint_teams`, `team_members`, `team_invites`). Капитан может смотреть «колоду» соло-игроков (`deck.php`). Стадию проекта участники отмечают через `save_progress.php` (`sprint_progress`).
3. Загрузка билдов: со страницы участника файл режется на куски и уходит в `upload_chunk.php` (S3, запись в `sprint_submissions`). Для голосования важна другая связка: игра публикуется как обычная игра платформы и привязывается к джему (`games.sprint_id`, вызов `/devs/jam_attach.php` из `participant.php`). Голосуют именно за записи в `games`.
4. Голосование: `jams/vote.php` показывает работы, `save_vote.php` принимает голоса в `jam_votes`. Условия (все в `save_vote.php`): окно `voting_start..voting_end` (у экспертов может быть длиннее), игра допущена модерацией, не своя и не из своей команды, организатор не голосует, голос даётся только после скачивания/запуска игры (`jam_plays`), бюджет 10 очков на джем (у эксперта 10 на каждую игру).
5. Итоги: момент объявления и номинации задаются в `swad/controllers/jams/jam_awards.php`. После `reveal_at` голосование закрыто, `vote.php` показывает победителей. Аналитика для админов — `admin_votes.php` и `results.php`. Фазы для карточек считает `phase_lib.php` (джем / голосование / завершён).

Файлы:

- `jams/index.php` — страница `/jams`, список всех джемов (~83 КБ). Серверный PHP + большой JS: карточки с фазами, кнопки «Участвовать», «Оценить», «Панель участника», форма создания джема, модалки команд. Таблицы: `sprints`, `sprint_participants`, `sprint_teams`, `team_members`, `sprint_experts`, `sprint_prizes`, `users`. Дёргает `create_sprint.php`, `join_sprint.php`, `get_progress.php`, `get_team.php`, `search_participants.php`, `invite_member.php`, `respond_invite.php`. Лезть сюда при правках списка джемов и карточек.
- `jams/participant.php` — панель участника, `/jams/participant.php?sprint_id=N` (~74 КБ). Если пользователь не участник — редирект на `/jams`. Показывает таймлайн, объявления, команду, колоду соло-игроков, прогресс, загрузку билда и прикрепление игры; Markdown объявлений разбирает собственная функция внутри файла. Таблицы: `sprints`, `sprint_participants`, `sprint_submissions`, `sprint_announcements`, `sprint_experts`, `sprint_progress`, `team_*`, `games`, `studios`, `staff`. Зовёт `save_progress.php`, `upload_chunk.php`, `deck.php`, `invite_member.php`, `respond_invite.php`, `leave_team.php`, `/devs/jam_attach.php`. Сюда лезть, если что-то не так у участника.
- `jams/admin.php` — админка джема, `/jams/admin.php?id=N` (~61 КБ). Доступ: ники из жёсткого списка `$allowedAdmins` в начале файла, остальные уходят на `/login` или получают отказ. Вкладки: участники, билды, объявления, жюри (внутренние и внешние), призы, настройки. Читает `sprints`, `sprint_participants`, `sprint_submissions`, `sprint_announcements`, `sprint_experts`, `sprint_prizes`, `sprint_teams`. Зовёт `add_judge`, `add_external_judge`, `add_prize`, `get_jam_judges` и ряд контроллеров вне `jams/`. ВНИМАНИЕ: часть адресов ведёт на несуществующие файлы (подробности ниже, в разделе про `swad/controllers/jams/`).
- `jams/admin_votes.php` — аналитика голосов для админки, `/jams/admin_votes.php?id=N`. Показывает сводку, лидерборд (байесовское среднее из вью `v_jam_leaderboard`), полный журнал «кто, за что, сколько, когда» и пики экспертов. Читает `jam_votes`, `games`, `sprints`, `sprint_experts`, `sprint_expert_picks`. Доступ: список админов или `global_role = -1`. Ссылается на `admin.php`, `vote.php`; на него ссылается `results.php`.
- `jams/results.php` — итоговая статистика джема, `/jams/results.php?id=N`. Что популярно и понравилось: агрегаты по играм, число «открытий» (`jam_plays`), пики экспертов; байес считается в PHP, без вью. Таблицы: `games`, `jam_votes`, `jam_plays`, `sprint_expert_picks`, `sprint_experts`, `sprints`. Доступ как у `admin_votes.php`. Это не публичные «итоги» с победителями — они на `vote.php`.

Выводит работы, прогресс голосования, фильтры/поиск, оценку в один клик, «Выбор эксперта», обратный отсчёт и после `reveal_at` — победителей по номинациям (через `jam_awards.php`). Выдаёт CSRF-токен и зовёт `save_vote.php`, `set_expert_pick.php`, `jam_play.php`, `presence.php`. Таблицы: `sprints`, `games`, `jam_votes`, `jam_plays`, `sprint_experts`, `sprint_expert_picks`, `studios`. Ссылки на неё стоят в `game.php` и в `/index.php` (баннер джема №12). Главное место для правок голосования и итогов.

Без авторизации, CORS `*`, кэш в файле во временной папке на 60 секунд, только агрегаты без персональных данных. Секции: overview, builds, timeline, teams, tech, geo, activity, leaderboard. Таблицы: `sprints`, `sprint_participants`, `sprint_teams`, `team_members`, `sprint_progress`, `games`, `jam_votes`, `jam_plays`, `deplex_builds`, `studios`. Описан в `apidoc.html`; в коде платформы вызывающих нет, это внешний API.

- `jams/jam1/index.php` — страница «первого джема» (`/jams/jam1`), ~96 КБ. Несмотря на «архив», это не статика: файл читает БД (`sprints`, `sprint_prizes`, `sprint_experts`, `sprint_participants`, `users`) и по умолчанию берёт `sprint_id = 12` (можно `?sprint=N`), сам считает фазу и рисует лендинг джема с призами, жюри и ссылками на `/jams/participant.php` и `/l4t`. ### swad/controllers/jams/

Здесь лежат серверные обработчики джемов: почти все они — маленькие JSON-эндпоинты, которые страницы из `jams/` (и отчасти `l4t/`) вызывают через `fetch`. Плюс две общие библиотеки: `phase_lib.php` (фазы и даты) и `jam_awards.php` (итоги). Общий стиль: проверяют сессию `$_SESSION['USERDATA']`, отвечают JSON `{success, message}`. Новые эндпоинты (`save_vote`, `presence`, `jam_play`) дополнительно проверяют CSRF через `swad/controllers/csrf.php`; старые (`join_sprint`, `add_prize`, `save_rating` и др.) — нет.

Известные проблемы с путями (важно новому разработчику): `admin.php` вызывает `/swad/controllers/remove_judge.php`, `/swad/controllers/send_announcement.php` и `/swad/controllers/jams/remove_external_judge.php` — в репозитории этих файлов по таким адресам нет. Файлы `remove_judge.php` и `send_announcment.php` (с опечаткой) лежат в `jams/`, и оба подключают `config.php` через `/../config.php`, то есть в несуществующий `swad/controllers/config.php` — перенос не доделан. Пока это не поправлено, снять судью и отправить объявление из админки, скорее всего, не получится (на проде может быть иначе — проверяйте).

Команды и участие

- `join_sprint.php` — регистрация в джеме. POST `sprint_id`; проверяет, что джем есть, не превышен `max_participants`, пользователь не записан; пишет в `sprint_participants`. Вызывается из `jams/index.php`.
- `create_team.php` — создать команду. POST/JSON: `sprint_id`, `team_name`, `team_desc`, `visibility`, `team_limit` (2–20); пользователь должен быть участником и не состоять в команде. Генерирует 8-символьный `invite_code`, пишет в `sprint_teams` и `team_members` (роль captain). Зовут `jams/index.php` и `l4t/js/l4x.js`.
- `get_team.php` — текущая команда пользователя. GET `sprint_id`; отдаёт участие, команду, состав и входящие приглашения (`sprint_participants`, `team_members`, `sprint_teams`, `team_invites`, `users`). Зовут `jams/index.php`, `l4t/js/l4x.js`.
- `invite_member.php` — капитан приглашает игрока. POST `team_id` + `username` или `user_id` (ищет и по Telegram-нику); приглашаемый должен быть участником спринта и свободен; пишет в `team_invites` и шлёт уведомление через `NotificationCenter.php`. Зовут `jams/index.php`, `jams/participant.php`, `l4t/js/l4x.js`. В репозитории есть отчёт `brokenpixel` об IDOR именно в этом файле — перед правками прочитайте его.
- `respond_invite.php` — принять или отклонить приглашение. POST `invite_id`, `action` (accept/decline); при принятии в транзакции проверяет лимит команды и обновляет `team_invites`, `team_members`. Зовут `jams/index.php`, `jams/participant.php`.
- `leave_team.php` — выйти из команды. POST `sprint_id`; удаляет из `team_members`; если команда опустела — удаляет её и отменяет приглашения, если ушёл капитан — передаёт роль следующему. Зовёт `jams/participant.php`.
- `search_participants.php` — поиск свободных участников для приглашения. GET `sprint_id`, `q` (от 4 символов), до 8 результатов из `sprint_participants` + `users`, кроме тех, кто уже в команде. Зовут `jams/index.php`, `l4t/js/l4x.js`.
- `deck.php` — «колода» соло-игроков для капитана. GET `sprint_id`; если пользователь не капитан — `eligible:false`; иначе отдаёт карточки тех, кто без команды, и сколько мест осталось (`team_members`, `sprint_teams`, `sprint_participants`, `team_invites`, `users`). «Соло» определяется по отсутствию строки в `team_members`, а не по `participant_type` (он ненадёжен). Зовёт `jams/participant.php`.

Прогресс и билды

- `save_progress.php` — сохранить прогресс разработки. POST/JSON: `sprint_id`, `percent` 0–100, `stage`, `engine`; команду редактирует только капитан, соло-игрок — себя. Пишет в `sprint_progress` (стадии из `jam_dev_stages()`). Зовёт `jams/participant.php`.
- `get_progress.php` — таблица прогресса всех команд и соло-участников. GET `sprint_id`; `sprint_teams`, `team_members`, `sprint_participants`, `sprint_progress`, `users`; подписи стадий берёт из `phase_lib.php`. Зовёт `jams/index.php`.
- `upload_chunk.php` — приём билда кусками. POST multipart (`sprint_id`, `chunk_index`, `total_chunks`, `file_name`, `file_size`, `chunk`); проверяет, что пользователь участник; собирает файл, заливает zip в S3 (бакет из константы `AWS_S3_BUCKET_JAMS`, класс из `swad/controllers/s3.php`) и пишет ссылку и размер в `sprint_submissions`. Константа `LARGE_THRESHOLD` (500 МБ) переключает режим для больших файлов. Не путать с `devs/upload_chunk.php` — это другой файл, для студий. Зовёт `jams/participant.php`.

Жюри, призы, объявления (админские)

- `add_judge.php` — назначить эксперта с аккаунтом. POST/JSON; права у организатора джема или админа; пишет в `sprint_experts` (сюда читают `vote.php`, `results.php` и др.). В комментарии описано, почему раньше писали не туда (в `jam_judges`).
- `add_external_judge.php` — добавить внешнего эксперта без аккаунта (имя, компания, роль, контакт, фото). multipart или старый JSON; пишет в `sprint_experts` (user_id пустой), фото грузит в S3; доступ по жёсткому списку админов (в коде пометка CONFIRM об актуальности списка). Зовёт `jams/admin.php`.
- `remove_judge.php` — снять эксперта с аккаунтом. POST JSON `sprint_id`, `user_id`; удаляет из `sprint_experts` и связанные пики. УСТАРЕЛО/СЛОМАНО по пути: см. выше; `admin.php` ходит по другому адресу. Внешних судей должен удалять несуществующий `remove_external_judge.php`.
- `get_jam_judges.php` — список судей по таблице `jam_judges`. GET `jam_id`. УСТАРЕЛО: после переезда судей в `sprint_experts` таблица `jam_judges` не пополняется, так что список из `admin.php` (`loadJudges`) может быть пустым или неполным; отдаёт текст ошибки БД в ответе.
- `add_prize.php` — добавить пустой приз. POST JSON `sprint_id`; вставляет в `sprint_prizes` следующий `place_num`. Зовёт `jams/admin.php`.
- `send_announcment.php` — создать объявление джема (имя файла с опечаткой). JSON `sprint_id`, `title`, `body`; доступ по списку админов; пишет в `sprint_announcements`, объявления потом читают `admin.php` и `participant.php`. Не работает из-за пути к config; админка вызывает другой адрес (см. выше).
- `save_rating.php` — УСТАРЕЛО: старая система оценок 0–10 по заявкам. Пишет в `sprint_ratings` и `sprint_vote_budgets`; ни одна страница на него не ссылается, голосование теперь идёт через `save_vote.php` и `jam_votes`. Хост не может оценивать. Кандидат на удаление после проверки.

Голосование и итоги

- `save_vote.php` — приём голосов (`/swad/controllers/jams/save_vote.php`). POST JSON `sprint_id`, `game_id`, `points` 0–10 (0 = отмена), CSRF обязателен; все условия голосования перечислены в схеме выше. Блокировка `GET_LOCK` защищает бюджет от гонок; пишет в `jam_votes`; читает `sprints`, `sprint_experts`, `games`, `team_members`, `jam_plays`. Подключает `jam_awards.php`: после `reveal_at` отвечает 409. Константы отладки `JAM_VOTING_FORCE_OPEN` и `JAM_EXPERT_WEIGHT` читаются из `config.php`; первую в проде включать нельзя. Зовёт `jams/vote.php`.
- `jam_awards.php` — единый конфиг итогов (библиотека). Функция `jam_awards_config()` — массив джемов с `reveal_at` (МСК), `sprint_id` и номинациями (`by = votes` — по баллам сообщества, `by = game` — выбор организаторов по названию или id). Сейчас настроен один джем (№12, итоги 2026-10-01 12:00). Чтобы добавить итоги другому джему — дописать элемент в массив. Функции `jam_awards_for`, `jam_awards_out`, `jam_awards_norm`; подключают `jams/vote.php`, `save_vote.php` и главная `/index.php` (баннер с отсчётом).
- `set_expert_pick.php` — поставить или снять «Выбор эксперта» для игры. POST JSON `sprint_id`, `expert_id`, `game_id`, `action` add/remove; права у админа (`global_role = -1`) или одобренного эксперта; пишет в `sprint_expert_picks`; читает `sprint_experts`, `experts`, `games`, `users`. Зовёт `jams/vote.php`.
- `jam_play.php` — отметка «игрок запустил работу» (play-to-vote). Эндпоинт только для веб-сборок (проверяет `games.platforms`), CSRF обязателен; для скачиваемых игр отвечает `skipped`. Главное: функция `jam_play_record()` — единственное место, пишущее в `jam_plays`; её напрямую вызывают `swad/controllers/download_game.php` и `download_deplex.php`. Зовёт `jams/vote.php`.
- `presence.php` — счётчик «сейчас ждут итогов». POST JSON `sprint_id`, `sid` (32 hex), CSRF; страница голосования шлёт «я тут» раз в ~20 секунд, онлайн = виден за последние 50 секунд, не больше 10 разных `sid` с одного IP. Сама создаёт таблицу `jam_presence` (`CREATE TABLE IF NOT EXISTS`) и чистит старые строки. Зовёт `jams/vote.php`.

Общая библиотека

- `phase_lib.php` — единый источник правды по фазам и датам. `jam_phase_ex()` даёт фазу (upcoming, registration, pre_jam, jam, post_jam, voting, finished), подписи и отдельный флаг «регистрация открыта» (окна могут пересекаться); также `jam_date_range()`, `jam_countdown()`, `jam_dev_stages()` (Идея…Готово). Подключают `jams/index.php`, `jams/participant.php`, `get_progress.php`, `save_progress.php` и `l4t/lib/match.php`. Не подключается из `jams/jam1/index.php`, там свой дубль `getPhase()`.

### devs/, expert/, finv2/, assetstore/ — общий обзор

Как работают URL: корневой `.htaccess` включает «чистые URL» — если файла `/devs/edit` нет, Apache отдаёт `/devs/edit.php`. Поэтому почти каждый `.php` в этих папках открывается по адресу без расширения (`/devs/edit?id=12`). Отдельных правил маршрутизации для этих четырёх папок в `.htaccess` нет (там только `/d/<имя>`, `/g/<id>`, `/player/<имя>` и т. п.). Во всех папках подключается `swad/config.php` (класс `Database`, соединение PDO) и используется `$_SESSION['USERDATA']`.

### devs/

Консоль разработчика (`/devs/`): студия создаёт проекты-игры, грузит билды и медиа, смотрит отзывы, аналитику, вишлисты, продвигает игры. Страницы с POST обрабатывают форму ДО подключения header.php, чтобы работали редиректы. Часть пунктов меню видна только модераторам/админам платформы (новые организации, эксперты, отчёты проверок, выдача достижений, уведомления). Есть и «служебные» эндпоинты без интерфейса (загрузка чанков, jam_attach, воркеры писем).

Любая новая страница консоли должна задать `$page_title`, `$active_nav` и подключить его; сюда лезть, чтобы добавить пункт меню.

### expert/

Экспертная система модерации игр. Публичная часть (`/expert/`): лендинг, заявка в эксперты, выборы экспертов голосованием. Закрытая часть (`/expert/admin/`): одобренные эксперты и админы (`global_role = -1`) голосуют по играм на модерации, админы ещё правят данные игр и одобряют заявки. Вердикт игры считается по голосам (порог «за» ~51%, «на доработку» даёт 12 ч на исправления, иначе отклонение), результат хранится в `moderation_reviews` и `games.moderation_status`, считается GQI. Страницы админки используют общий `_sidebar.php`.

- `index.php` — лендинг «Станьте экспертом» (`/expert/`): статистика (`experts`, `moderation_reviews`, `games`), текущий период выборов, ссылки на заявку и `/expert/vote`.
- `expert-apply.php` — форма заявки в эксперты; показывает статус, окно приёма (`expert_elections`) и таймер. POST уходит в `submit-expert.php`.
- `submit-expert.php` — сохраняет заявку в `experts`, проверяет, что набор открыт и заявки ещё не было, в фоне вызывает `notify_expert.php` (loopback) и редиректит на `thanks`.
- `notify_expert.php` — фоновое письмо о новой заявке (только внутренние вызовы, `send_email.php`).
- `thanks.php` — статичная страница «Заявка принята».
- `vote.php` — выборы экспертов (`/expert/vote`): AJAX голосование за кандидатов (`expert_votes`, `experts`), нельзя за себя, повторный клик снимает голос.
- `submit-moderation.php` — ДУБЛЬ/устаревшая копия `expert/admin/submit-moderation.php` (приём оценки + пересчёт вердикта по порогу 51%). Форма игры (`moderation-game.php`) шлёт на относительный `submit-moderation` внутри `admin/`, на корневой файл никто не ссылается. Сверить и удалить, если не нужен.
- `admin/_sidebar.php` — сайдбар админки (меню, счётчики ожидающих экспертов и игр, свои стили). Перед подключением задаётся `$active_page`.
- `admin/index.php` — дашборд: количество экспертов, игр на модерации по статусам, график поступления за 14 дней. Доступ: одобренный эксперт или админ.
- `admin/moderation.php` — список игр на модерации с поиском, сортировкой и фильтром по джему (`games`, `sprints`, `deplex_builds`, `deplex_projects`); на него ссылается `swad/controllers/auto_moderation.php`.
- `admin/moderation-game.php` — страница оценки одной игры (`?id=`): материалы, билд и результат антивируса, чек-лист, форма голоса; показывает рецензии других и таймлайн изменений (`game_changelog_timeline.php`, `dev_contacts.php`). Сюда же ссылаются `devs/scan-reports.php` и `devs/experts.php`.
- `admin/submit-moderation.php` — ГЛАВНЫЙ обработчик голоса эксперта: пишет `moderation_reviews`, считает GQI (`recalcGQI`), проверяет итог (`checkModeration`), письмом уведомляет разработчика (`staff`/`users`).
- `admin/update-review-1h.php` — JSON: правка своей рецензии в течение часа после отправки с пересчётом вердикта; вызывается из `all-reviews.php`.
- `admin/all-reviews.php` — все оценки модерации (эксперты видят агрегаты, админы — полные рецензии с авторами), пагинация и фильтры.
- `admin/expert-requests.php` — админ одобряет/отклоняет заявки и смотрит экспертов (AJAX на себя же).
- `admin/games.php` — только для админов: правка «сырых» данных любой игры (статус, описание, жанры, видимость), пишет changelog (`game_changelog.php`).
- `admin/monthly-experts.php` — JSON-API очереди «экспертов месяца» (`expert_monthly`: enqueue/dequeue/roll рандомом, 10 мест). Интерфейса и ссылок на него в коде нет — похоже на недоделанную/неподключённую фичу.
- `admin/update-content-rating.php` — POST правка маркировки контента (`games.content_descriptors`, `content_rating_verified`). Ссылок на него в репозитории не нашлось — возможно, отключён.
- `admin/update-expert.php` — JSON одобрение/отклонение эксперта по id. Устарел: `expert-requests.php` делает то же сам, вызывающих нет.

### finv2/

Платежи на ЮKassa (SDK из `vendor/autoload.php`) и немного платёжной истории. Три сценария: покупка игры (`game_orders`, библиотека `library`), «оплата инфраструктуры/поддержка» игры (`infra_payments`), слоты продвижения (`game_promotions`) и подписка на тариф (`subscriptions`). Схема везде одинакова: создать платёж → редирект на ЮKassa → страница `success*` перепроверяет статус через API (на случай, если вебхук не дошёл) → обновляет БД. Ключи магазина берутся из конфига, в этих файлах их не выписываем.

- `index.php` — страница тарифов подписки (`/finv2/`); определяет текущий план из `subscriptions`, кнопка ведёт на `billing/checkout.php?plan=indie_pro`.
- `billing/checkout.php` — создаёт подписку `pending`, платёж ЮKassa с чеком (нужен email пользователя) и редиректит на оплату.
- `billing/yookassa_webhook.php` — вебхук подписок: по `metadata.subscription_id` активирует `subscriptions`, ставит срок и шлёт письмо. Адрес, видимо, прописан в кабинете ЮKassa.

- `payment_modal.php` — подключаемый фрагмент: модальное окно оплаты игры/донатов на странице игры (JS опрашивает `check_payment_game.php`, создаёт платежи). Переменные `$game`, `$studio_payment_data` задаёт страница игры.

- `webhook_debug.log` — лог отладки `game_webhook.php` (в основном «FATAL: Invalid JSON», апрель 2026). Логи в репозитории не нужны; безопасно очищать.

### L4T, Fid, Chat, GDDB — путеводитель по папкам

Корневой `.htaccess` делает две вещи: «красивые» URL без `.php` (`/chat/api` -> `chat/api.php`, если файла нет) и закрывает все «точечные» файлы (`.env`, `.git`) ответом 404. Для этих папок в нём есть одно особое правило: `/fid/post/123` -> `fid/index.php?post=123`. У `l4t/` есть свой `.htaccess`, у `chat/`, `fid/` и `gddb/` — нет.

### l4t/ — «Looking for Team»

### l4t/
L4T — сервис Dustore для портфолио и поиска людей в команду или на джем. Открывается по `/l4t/`. Своя база называется `desl4t` и подключается через `Database::connect('desl4t')`. Принцип устройства: `index.php` — тонкая страница-разметка, данные берутся из `lib/`, куски HTML лежат в `views/`, запись идёт через `api/`, поведение — в `js/`. Связанный бэкенд, который описывает другой агент: `swad/controllers/l4t/` (создание заявок, отклики, CSRF) и `swad/static/elements/header.php` (ссылка в шапке).

- `.htaccess` — правила маршрутизации внутри /l4t/. Закрывает точечные файлы, а также `lib/`, `views/` и всё, что начинается с `_` (их подключают только через include). Превращает `/l4t/<ник>` в `index.php?username=`, `/l4t/<ник>/cv` в `cv.php?username=`, `/l4t/cv/<16 hex-символов>` в `cv.php?t=` (именная ссылка на резюме). Лезть сюда, если нужен новый красивый URL или страница отдаёт 403.
- `index.php` — главная страница L4T (940 строк). Один файл, который по URL показывает свой профиль, чужой профиль (`/l4t/<ник>`), биржу заявок, «Мои заявки», отклики, «Связи», «Мои позиции», колоду «Для тебя»; вкладка выбирается через `?tab=`. Есть также `?action=create_bid&source=jam&jam_id=N` и `?action=create_team&jam_id=N` для заявки или команды под джем. Подключает все `lib/*`, читает таблицы `bids`, `responds`, `sprints`, `users`. Начинайте отсюда, когда нужно понять, как устроена страница.
- `_bid_card.php` — одна карточка заявки (партиал). Её рисуют и `index.php` (первая страница ленты), и `api/feed.php` (догрузка и поиск), поэтому карточка выглядит одинаково. Все данные лежат в одном `data-bid` JSON, а модалку читает `js/l4x.js`. Менять здесь, если нужно поменять вид карточки.
- `cv.php` — резюме одной страницей для печати (`/l4t/<ник>/cv` публично, `/l4t/cv/<токен>` по именной ссылке из `share_links` со счётчиком открытий). Светлая печатная вёрстка без шапки сайта, PDF получается через Ctrl+P. Данные берёт из `lib/profile.php` и `lib/extras.php`. Ссылки создаются на вкладке «Связи» (`op=link_create`).
- `organizer.php` — инструменты организатора (`/l4t/organizer.php`, нужен логин): мероприятия, сканер QR-пропусков на входе (камера телефона, BarcodeDetector или jsQR) и очереди джемов с автосборкой команд. Использует `lib/extras.php` (`l4t_events`, `event_checkins`) и `lib/match.php` (`jam_queue`). Ссылка на него стоит во `views/network.php`.
- `req.php` — статичная HTML-заготовка «Request #1024» (демо-дизайн заявки с Google Fonts). Нигде не подключается, данных из БД не берёт. Устаревшее, это макет, не трогать.
- `paper.php` — статичная HTML-заготовка заявки, такой же макет, как `req.php`. Ссылается на `response.php?id=1024`. Устаревшее, не используется.
- `response.php` — статичная заготовка формы «Response» (один из старых макетов). Живую логику откликов давно заменили `swad/controllers/l4t/respond_bid.php` и `api/action.php`. Устаревшее.

### l4t/core/
Нижний слой для подключения к базе. Остался от первой версии: раньше здесь жили собственный .env и свой PDO. Сейчас он только подключает общую фабрику `Database` из `swad/config.php`.

- `db.php` — подключение к базе `desl4t`; определяет глобальный `$pdo` и больше не хранит паролей (раньше читал .env, который отдавался по HTTP). Подключают его старые скрипты вроде `getall.php`. Новый код должен брать `Database::connect('desl4t')`, а не этот файл.
- `getall.php` — отдаёт JSON со всеми заявками (`SELECT * FROM bids`, без фильтров и авторизации). Относится к первой версии; живая лента теперь идёт через `api/feed.php`, а комментарий в `swad/controllers/l4t/respond_bid.php` лишь вспоминает «api/getall.php». Устаревшее; закрыть, если не нужно.

### l4t/lib/
Логика и данные, без вёрстки. Каждый файл — набор функций или классов, которые подключает `index.php`. Все файлы проверяют через `information_schema`, накатана ли нужная миграция, и при отсутствии таблицы возвращают пустоту, поэтому страница не падает.

- `profile.php` — всё для страницы профиля одним объектом `$P`: профиль, заявки пользователя, статистика, значки, игры, студии, друзья, просмотры. Читает много таблиц (`profiles`, `bids`, `responds`, `games`, `badges`, `friends`, `profile_views` и др.). Сюда лезть, если на профиле нужен новый блок данных.
- `feed.php` — выборка ленты биржи (`l4x_feed`, `l4x_feed_tags`, `l4x_authors`, `l4x_has_col`), по 20 штук на страницу. Одна и та же функция работает для первой страницы (`index.php`) и догрузки (`api/feed.php`), поэтому фильтры не расходятся.
- `extras.php` — «вторая волна»: навыки, опыт, титры в играх, рекомендации, статусы откликов, QR-пропуска, контакты, мероприятия, сохранённые поиски, ссылки на резюме. Основной слой записи для `api/action.php`, таблицы `skills`, `user_skills`, `work_experience`, `credits`, `recommendations`, `contacts`, `share_links`, `l4t_events` и др. Требует миграцию 007.
- `match.php` — подбор: лента «Для тебя», поиск людей, очередь джема, автосборка команд. Это честный счётный скоринг («совпало: Unity, C#»), без ML, с объяснением совпадения. Использует `bids`, `user_skills`, `jam_queue`, `sprint_teams`.
- `market.php` — самый большой файл (1275 строк): L4T как рынок «спрос × предложение». Заявка — спрос, `offers` — предложение «Я могу», совпадения по навыкам, свайпы, приглашения, сделки, котировки и стакан. Таблицы `offers`, `offer_skills`, `matches`, `swipes`, `invites`. Лезть сюда при любых изменениях рынка и колоды.
- `icons.php` — SVG-спрайт L4T (`l4x_icon()`, `l4x_sprite()`), как в Fid: 24x24, контур currentColor. Вставляется на страницу один раз.

### l4t/api/
Три эндпоинта, которые зовёт браузерный JS. Формат ответа везде `{ok:...}` или `{ok:false, error}`.

- `action.php` — единая точка записи и чтения для новых функций (`/l4t/api/action.php`). Диспетчер по параметру `op` (около 50 операций: `deck`, `swipe`, `offer_save`, `pos_view`, `exp_save`, `rec_save`, `link_create`, `checkin`, `queue_join`, `teams_form`, `quotes`, `book` и т.д.). Одна проверка авторизации и один CSRF; сама логика в `lib/extras.php`, `lib/match.php`, `lib/market.php`. Вызывают его `js/l4x-pos.js`, `js/l4x-market.js`, `js/l4x-more.js`. Новую операцию добавлять сюда.
- `feed.php` — отдаёт готовый HTML карточек ленты для поиска, тегов и «Показать ещё» (рендерит через `_bid_card.php`). Зовёт `js/l4x.js`.
- `bid_view.php` — считает просмотр заявки: один зритель, одна заявка, один раз в сутки (`bid_views`), автор не накручивает.

### l4t/views/
Куски HTML, которые `index.php` подключает через `require` и которым передаёт готовые переменные (названы в шапке каждого файла). Логики запросов тут нет.

- `foryou.php` — колода «Для тебя»: одна карточка, влево пропустить, вправо откликнуться; джемы отдельной полосой сверху. Саму колоду рисует `js/l4x-pos.js` из `op=deck`.
- `positions.php` — «Мои позиции»: слева заявки, предложения и приглашения, справа кандидаты на выбранную позицию. Рендер на стороне `js/l4x-pos.js`.
- `positions_matches.php` — совпадения: пары «моя позиция × чужая» по группам (ждут ответа, ждём другую сторону, сделки). Данные из `lib/market.php`.
- `positions_offers.php` — скрытая форма «Я могу» (создание предложения), открывается в боковой панели. Отправка через `js/l4x-market.js` -> `op=offer_save`.
- `market_book.php` — каркас «стакана» рынка (котировки, стакан, лента сделок). Содержимое рисует `js/l4x-market.js`, опрос `op=quotes|book` каждые 20 секунд.
- `network.php` — вкладка «Связи»: контакты, ссылки на резюме, сохранённые поиски, мероприятия, ссылка на `organizer.php`.
- `profile_aside.php` — верх боковой колонки профиля: «Вы всё ещё открыты?», условия работы, ожидающие подтверждения.
- `profile_blocks.php` — навыки, опыт, титры, рекомендации в основной колонке профиля; уровни навыков «учусь / уверенно / эксперт».
- `profile_offers.php` — «Готов взять»: активные предложения человека на его профиле; гость может предложить задачу.
- `game_credits.php` — блок «Над игрой работали» на странице игры; подключается не из l4t, а из корневого `game.php`. Любой сбой просто не рисует блок. Связь L4T с каталогом игр.

### l4t/js/
Клиентский код. Всё работает поверх объекта `window.L4X` (конфиг из PHP) и общего `window.L4XUI` из `l4x.js`, поэтому `l4x.js` подключается первым.

- `l4x.js` — база страницы: один делегированный обработчик кликов по `[data-act]`, модалки, вкладки, поиск и догрузка ленты, отклики. Экспортирует `L4XUI` для остальных скриптов.
- `l4x-pos.js` — боковая панель (создание, правка, просмотр), «Мои позиции», колода «Для тебя», модерация.
- `l4x-market.js` — рынок: котировки, стакан, лента сделок, совпадения, прямые предложения; опрос API каждые 20 секунд только при видимой вкладке.
- `l4x-more.js` — навыки, опыт, титры, рекомендации, QR (визитка, резюме, пропуск), контакты, ссылки на резюме, очередь джема.

### chat/ — чаты

### chat/
Мессенджер (`/chat/`: личные чаты, чаты студий, системные «Уведомления», истории, реакции, вложения, блокировки). Одна и та же разметка (`_markup.php`) и один `chat.js` работают и на десктопе, и в мобильном PWA (`/m/chat`, `m/views/chat.php`); на телефоне `index.php` перенаправляет туда. Все данные идут через `api.php` (`?action=...`), живое обновление — поллинг и WebSocket (`/ws?ticket=` от `chat/ws_ticket.php`). Web Push устроен так: PHP кладёт задачи в `push_outbox`, Node-воркер `pwa/push-worker.js` забирает их через `push_outbox.php`. Таблицы: `conversations`, `messages`, `conversation_participants`, `chat_files`, `chat_stories`, `message_reactions`, `chat_blocks`, `push_subscriptions` и др.; многие создаются на лету (`CREATE TABLE IF NOT EXISTS`). Файлы `ws_helpers.php` и `ws_ticket.php`, на которые ссылается код, в репозитории отсутствуют (не закоммичены): `api.php` проверяет их через `is_file`/`function_exists`.

- `index.php` — страница чата (`/chat/`, параметры `?to=`, `?studio=`, `?conversation=`, `?system=` — из пушей и ссылок). Требует логин, на телефоне редиректит в `/m/chat`, подключает `_markup.php`, `chat.js`, публичный VAPID-ключ.
- `api.php` — весь серверный API чата (1100 строк, JSON, `?action=`): `list`, `thread`, `send`, `start`, `delete_message`, `block_user`, `story_*`, `upload_init/commit/proxy`, `pin`, `react`, `mark_read`, `wallpaper_*`, `settings` и др. Зовут его `chat.js` и сервис-воркер `sw.js` (мимо кеша). Любое изменение серверного поведения чата — сюда.
- `chat.js` — клиент мессенджера (1627 строк): список, тред, ответы и свайпы, пины, контекстное меню, вложения, отправка, настройки, поиск. Конфиг берёт из `window.CHAT_CFG`. Один на десктоп и мобилку.
- `file.php` — шлюз к вложениям `?id=N[&thumb=1]`: проверяет, что вы владелец или участник беседы, и редиректит на подписанную ссылку S3. Менять при проблемах с доступом к файлам.
- `_markup.php` — общая HTML-разметка мессенджера (десктоп и `/m/chat`), блоки под `$mobileUI`. Подключают `index.php` и `m/views/chat.php`.
- `_helpers.php` — общие функции: аватары, студии пользователя (`staff`, `studios`), карточки пользователей, ключи диалогов `dm_key`/`studio_key`. Подключается почти везде.
- `_files.php` — вложения в S3 (схема как в Telegram): запись `chat_files` в состоянии pending, подписанный PUT, проверка размера, подписанный GET. Использует `api.php` и `file.php`.
- `_crypto.php` — шифрование тела сообщений при хранении (`msg_encrypt`/`msg_decrypt`). Это не сквозное шифрование, ключ лежит на сервере; защищает дамп БД. Ключ не выписываю.
- `_blocks.php` — чёрный список в личных чатах (таблица `chat_blocks`): после блокировки писать нельзя, история остаётся.
- `_reactions.php` — реакции-эмодзи (одна на человека на сообщение, повторный тот же эмодзи снимает).
- `_stories.php` — «истории» на 24 часа (фото и текстовые карточки), видны друзьям из `friends`; просмотры в `chat_story_views`.
- `_bridge.php` — общий секрет локальных мостов Node <-> PHP (из файла, env или производный от VAPID-ключа). Используют `api.php` и `push_outbox.php`.
- `_push_config.php` — единый поиск VAPID-ключей для PHP и Node-воркера (несколько файлов и env). Основа для `_vapid.php`, `_bridge.php`.
- `_vapid.php` — отдаёт публичный VAPID-ключ для подписки на push (`vapid_public_key()`), его зовут `index.php` и `m/views/chat.php`.
- `push_helpers.php` — постановка push в очередь `push_outbox` (`push_enqueue_user`, `push_enqueue_for_conversation`); раньше был пустым файлом, из-за чего пуши молча не слались.
- `push_subscribe.php` — сохраняет push-подписку браузера (нужен логин); вызывают `sw.js` и `pwa/push-client.js`.
- `push_outbox.php` — выдача очереди push Node-воркеру (`pwa/push-worker.js`), защищена общим секретом моста; БД выбирается по Host запроса.
- `push_check.php` — страница «почему не приходят пуши» из пяти звеньев (ключ, подписка, воркер, очередь, статус); детали видны только админу.
- `push_doctor.php` — то же, но CLI-диагностика (`php chat/push_doctor.php [--send=ID]`), только из консоли.

### api/
Папка с «голыми» PHP-эндпоинтами, которые отдают JSON. Часть из них — публичное API для внешних программ (загрузчик билдов студий, клиент HidL), часть — внутренние вызовы фронта (друзья, лента, вишлист). Единого роутера нет: один файл — один URL `/api/<имя>`. Старые эндпоинты (`get_*`) лежат без авторизации и во многом устарели.

- `auth.php` — выдача доступа к S3 для загрузчика билдов (URL `/api/auth`). Принимает POST JSON `{token}`, ищет студию в таблице `studios` по токену и в ответ отдаёт параметры S3 (endpoint, bucket, prefix `studio_<id>`) вместе с ключами доступа. Нужен внешнему инструменту загрузки (Deusplex/chunk-дистрибуция); ключи захардкожены — трогать с осторожностью и убрать в конфиг.
- `check_session.php` — редирект на локальный клиент HidL. Берёт `$_SESSION['USERDATA']['id'] ` и шлёт на `http://127.0.0.1:5000/callback?user_id=...`. Нигде в репозитории не вызывается, похоже на заготовку/устарело.
- `detector.php` — пустой файл (0 байт). Упоминается только в `l4t/organizer.php`; можно удалять после проверки.
- `friends.php` — друзья (`/api/friends.php`, POST/GET с параметром `action`). Действия: `send`, `accept`, `decline`, `remove`, `cancel` (только POST + CSRF) и `list`, `incoming`, `outgoing` (GET). Отвечает JSON `{success, error|message, friends|requests}`; логика в классе `User` (`swad/controllers/user.php`), таблица `friends`; лимит 20 заявок в час. Вызывается из `fx.php`-страниц и `swad/js/fx-player.js` (профиль игрока).
- `fx.php` — главный API «Fid Core» (лента, посты, статьи, комментарии, реакции, опросы, подписки, DustHunt, загрузка фото). Единая точка с `action`: `feed`, `post`, `comments`, `thread`, `mentions`, `hunt`, `create`, `edit`, `delete`, `pin`, `lock`, `react`, `comment`, `comment_delete`, `comment_like`, `vote`, `follow`, `report`, `views`, `hunt_join/leave`, `upload`. Ответ `{ok:true,...}` или `{ok:false,error:код}`; мутации — только POST + CSRF; карточки приходят уже готовым HTML (`swad/fx/render.php`), логика в `swad/fx/core.php`. Вызывается из `swad/js/fx.js`, `fx-editor.js`, `fx-player.js` и мобильной версии. Сюда лезть при любых изменениях ленты.
- `game_preview.php` — обложка игры по id (`?id=`). Читает `games.path_to_cover`, отдаёт JSON (без заголовка Content-Type). Вызовов в репозитории нет — устарело.
- `games.php` — список игр студии (`?studio_id=` → `id, name, description`). Только GET, таблица `games`. Вызовов не найдено, дублирует `get_studio_games.php`; кандидат на удаление.
- `get_all_games.php` — публичный каталог опубликованных игр. GET `limit` (1–100), `offset`, `platform`, `search`; отдаёт `games.*` + `developer_name` из `studios`, только `status='published'` и не скрытые. Для внешних клиентов; из кода сайта не вызывается.
- `get_all_users.php` — список всех пользователей (`id`, `username`). Используется в `jams/admin.php`. Содержит баг: обращается к `telegram_username`, которого нет в SELECT.
- `get_game.php` — одна игра по `?id=` (все поля `games`, скриншоты/системные требования разобраны из JSON). Публичный, GET; сайтом не вызывается, нужен для внешних клиентов.
- `get_studio_data.php` — студия по `?studio_id=`: `id, name, email` (из `studios.contact_email`).
- `get_studio_games.php` — все игры студии (`games.developer = studio_id`) целиком. Публичный GET; дублирует `games.php`, но с полными данными; в коде не используется.
- `get_user.php` — задумывался как поиск юзера по passphrase. Сломан (использует несуществующую `$studio`, сравнивает хеш с новым `password_hash`, который каждый раз разный) — фактически мёртвый код. Используется только именем в чужих файлах (`chat/*`, `devs/staff.php` ссылаются на другое `get_user`, не на этот файл).
- `validate_token.php` — проверка токена студии (URL `/api/validate_token`). POST JSON `{token_hash}`; сверяет с `studios.api_token` (там хранится хеш) и возвращает `{status:'ok', studio_id, studio_name}` либо 401. Вызывается из `finv2/index.php`; нужен загрузчикам/инструментам разработчика.

### api/hidl/
API для HidL — десктопного клиента-лаунчера Dustore, который слушает на `127.0.0.1`. Авторизация идёт через «токен десктопа» в таблице `desktop_tokens`; присутствие игрока хранится в `user_activity`. Заголовок для токена — `X-Desktop-Token`.

- `hidl_auth.php` — вход клиента (URL `/api/hidl/hidl_auth`). Если на сайте нет сессии — отправляет на `/login?backUrl=...`; иначе создаёт случайный токен, пишет в `desktop_tokens` и редиректит на `http://127.0.0.1:8000/auth_success?token=...` (вывод токена через `echo` перед редиректом — лишнее). Упоминается в `game.php`.
- `check_token.php` — проверка токена: принимает его из GET/POST или заголовка, отвечает `{ok, user_id, username, tg_username}`. Дёргает клиент HidL.
- `activity.php` — «heartbeat» клиента: POST JSON `{app}` + заголовок токена, делает upsert в `user_activity` (текущее приложение, `last_seen`). Отвечает `{ok:true}`.
- `status.php` — публичный список статусов: для каждого юзера `online`/`offline`/`playing <app>` (offline если не было сигнала больше 30 с). Для витрины/клиента.

### api/mobile/
Старое «мобильное API» (под нативное приложение): токен — просто base64 от JSON `{id, exp}` без подписи. Давно не используется ни сайтом, ни `m/` (там своя авторизация), поэтому считается устаревшим и небезопасным.

- `login.php` — старый вход по email для нативного приложения. Никем не вызывается, устарел, кандидат на удаление.
- `library.php` — старая библиотека игрока по `?token=` для нативного приложения. Работает по устаревшей схеме (столбец `user_id`, в новой — `player_id`). Устарело, кандидат на удаление.

### api/push/
Web Push-подписки. Живая часть — только `subscribe.php`; остальное — остатки старого Node-сервера уведомлений. Актуальную отправку пушей сейчас делает `chat/_vapid.php` и общий `/sw.js` (см. комментарий в `swad/static/elements/header.php`).

- `subscribe.php` — сохраняет подписку браузера (`/api/push/subscribe.php`). POST JSON `{endpoint, keys:{p256dh, auth}}`, пользователь берётся из сессии; upsert в таблицу `push_subscriptions` (+ user_agent). Отвечает `{ok:true}` или 401.
- `send.php` — по сути не PHP: внутри `<script>` лежит копия Node-обработчика `/send`. При открытии просто выведет HTML-тег — мусор, удалить.
- `index.js` — Node/Express-сервер старого push-сервиса: `POST /send {user_id,title,body,url}` берёт подписки из `push_subscriptions` и шлёт через `web-push`. Нужны `.env` с VAPID-ключами и БД (в репозитории `.env` быть не должно). Скорее всего не запущен — устарел.
- `package.json` — зависимости этого Node-сервера (express, web-push, dotenv, mysql2). Нужен только если оживлять `index.js`.
- `package-lock.json` — лок-файл npm к нему (генерируемый, руками не править).

### api/wishlist/
- `toggle.php` — сердечко «сохранить игру» (`/api/wishlist/toggle.php`). POST JSON `{game_id}`, нужна сессия; добавляет/удаляет запись в вишлисте и отвечает `{ok, action:'added'|'removed', total}`. Вызывается из `game.php`, `library.php` и `swad/static/elements/gp_like_button.php`. В мобильной версии используется свой `m/api/wishlist.php`.

### m/
Мобильная версия сайта в виде PWA, открывается по `/m/...`. Это не отдельный проект: она использует ту же БД, сессию, классы (`Game`, `User`, `FxPages` из `swad/`) и общий service worker `/sw.js`; своё — только оболочка, вёрстка и маршруты. Основной сайт отправляет телефоны сюда через `swad/controllers/mobile_redirect.php` (сопоставляет пути вроде `/game/5` → `/m/game/5`). Разметку карточек делает PHP (`m_card`), JS получает готовый HTML.

- `.htaccess` — правила для `/m/`: если файл или папка существуют — отдать как есть, иначе всё на `m/index.php`. Благодаря этому работают красивые URL вроде `/m/game/123`.
- `index.php` — роутер. Разбирает путь, допускает страницы `home, catalog, game, library, profile, search, developer(dev), chat, login, media, player`, подключает `views/<страница>.php` в буфер, потом оборачивает в `layout/shell.php`. Неизвестный путь → редирект на `/m/`. Сюда лезть, чтобы добавить новую страницу.
- `lib.php` — общие функции мобилки: восстановление сессии по куке `auth_token` (`m_restore_session`, важно для iOS), карточка игры `m_card`, выборка `m_games` (через `Game::queryGames`), цены, обложки, фильтры каталога, пустые состояния, подключение Fid (`m_fx*`). Любая мелочь в логике карточек/каталога — здесь.
- `manifest.json` — манифест PWA (имя, `start_url=/m/?source=pwa`, цвета, иконки, ярлыки Чаты/Каталог/Мои игры). Меняется при смене иконок/названия.
- `sw.js` — «самоуничтожающийся» service worker: старый воркер со scope `/m/` теперь удаляет себя и кэши, чтобы работал общий `/sw.js` в корне. Не удалять — у пользователей ещё может быть старая регистрация.

### m/layout/
- `shell.php` — общая оболочка страницы: `<head>`, шапка, нижнее меню (Игры · Медиа · Чаты · Профиль; вкладка «Медиа» появляется сама, если есть `views/media.php`), подключение `css/app.css` и `js/app.js`. Получает переменные (`$title`, `$bodyClass`, `$hideNav` …) от роутера и вьюх.

### m/views/
Страницы приложения; каждая — PHP-фрагмент, подключаемый `index.php`.

- `home.php` — витрина (`/m/`): герой-карусель, ленты «популярное/новое/бесплатное/для телефона», жанры, «продолжить играть» из `library`.
- `catalog.php` — каталог (`/m/catalog`): фильтры жанр/сортировка/цена, бесконечная подгрузка через `m/api/games.php`.
- `game.php` — страница игры (`/m/game/<id>`): галерея, трейлер, описание, кнопка (CTA), вишлист; самая большая вьюха. Скрывает нижнее меню, вместо него панель действий.
- `library.php` — «Мои игры» и вишлист (`/m/library`, `?tab=wishlist`); данные из `library`, `wishlists`; требует вход.
- `search.php` — поиск (`/m/search`): строка, жанры; результаты подгружает `api/search.php`.
- `profile.php` — профиль и настройки приложения (`/m/profile`): счётчики, уведомления (push), установка PWA, passkey.
- `login.php` — собственный вход мобилки (`/m/login`): почта+пароль, passkey, Telegram через редирект (не popup, ради iOS PWA); использует `m/js/auth.js`.
- `chat.php` — мессенджер (`/m/chat`): тот же `chat.js` и разметка, что на десктопе (`chat/_markup.php`, `chat/_helpers.php`), поверх — `css/chat-m.css`.
- `developer.php` — страница студии (`/m/dev/<тикер>` или `/m/developer/<id>`): использует `FxPages::studio` из `swad/fx/pages.php` (тот же хаб, что на сайте).
- `player.php` — страница игрока (`/m/player/<ник>`): `FxPages::player`; без ника — редирект на свою страницу.
- `media.php` — «Медиа» (`/m/media`, `?post=ID`): лента Fid в приложении, `FxPages::fid`.

### m/api/
Внутренние JSON/HTML-эндпоинты мобилки (URL `/m/api/<файл>`; `.htaccess` отдаёт существующие файлы напрямую).

- `auth.php` — вход и passkey (WebAuthn без библиотек): POST `action` = `login`, `wa_login_options`, `wa_login`, `wa_reg_options`, `wa_register`, `wa_list`, `wa_delete`. Итог — та же сессия и кука `auth_token`, что у десктопа; проверка CSRF по источнику запроса. Вызывается из `m/js/auth.js`; здесь править логику входа с телефона.
- `games.php` — следующая страница каталога: GET с фильтрами каталога, ответ `{html, next, done}`. Вызывается из `app.js` на странице каталога.
- `search.php` — живой поиск: GET `q`, отдаёт готовый HTML (text/html). Вызывается `app.js` (`/m/api/search.php?q=`).
- `search_results.php` — не эндпоинт, а общий кусок разметки результатов (игры + студии); напрямую по URL отдаёт 404. Подключается из `search.php` и `views/search.php`.
- `wishlist.php` — сердечко на странице игры: POST `game_id`, `on=1|0` (явное состояние, а не toggle), таблица `wishlists`; ответ `{ok:..}`, 401 без входа. Вызывается из `app.js`.

### m/js/
- `app.js` — вся клиентская логика: регистрация `/sw.js`, speculation rules и View Transitions, карусели, живой поиск, подгрузка каталога, вишлист, установка PWA. Без фреймворков.
- `auth.js` — вход: форма почта/пароль, passkey (WebAuthn), Telegram, управление ключами в профиле; ходит в `/m/api/auth.php`.

### m/css/
- `app.css` — основной стиль PWA (тёмная фиолетово-малиновая палитра, нижнее меню, ленты, карточки) + `@font-face` шрифта Onest.
- `chat-m.css` — «кожа» чата для телефона, грузится после `swad/css/chat.css` только на `/m/chat`.
- `fx-m.css` — подгонка Fid (лента, хабы студий/игроков) под оболочку PWA; поверх `swad/css/fx.css`.

### m/fonts/
Группа из 4 файлов `onest-*.woff2` (cyrillic, cyrillic-ext, latin, latin-ext) — шрифт Onest, разбитый по диапазонам Юникода, подключается в `app.css`; работает без Google Fonts.

### m/icons/
Группа картинок PWA: `icon-192.png`, `icon-512.png`, `maskable-512.png` (манифест и пуши), `apple-180.png` (иконка на экран iOS, `shell.php`), `logo-appolo.png` (логотип в шапке и на входе). `logo.webp` — старый логотип, в коде мобилки не используется (кандидат на удаление).

### mini-server/

Здесь лежит мессенджер MINI целиком: Node.js-сервер («MINI ID») и сам клиент-PWA (HTML/JS/CSS). Сервер хранит аккаунты с глобальными @никами и каталог публичных ключей, а «релей» разносит зашифрованные сообщения между Яндекс.Дисками пользователей — клиент в режиме «белых списков» ходит только на Яндекс, а не на наш сервер. Нужен Node.js ≥ 22.5 (встроенный `node:sqlite`; на старом Node подхватывается `better-sqlite3`) и пакет express. Запуск: `cp config.example.json config.json`, заполнить OAuth-данные Яндекса, `npm install`, затем `npm start` (сайт на порту 3000, HTTP) и отдельным процессом `npm run relay` (опрос Дисков каждые ~20 с по HTTPS к API Яндекса). Внимание: `package.json` в mini-server/ в git не попадает (он в корневом .gitignore), поэтому команды npm из README в чистом клона не заработают без него. С остальным Dustore связан слабо: в репозитории есть только запись о приложении MINI в `source.json` (IPA-источник для iOS), общего кода и общей БД нет.

- `README.md` — документация сервера на русском.
  Требования к Node, настройка OAuth на oauth.yandex.ru, запуск, формат файлов обмена на Диске (`MINI/outgoing`, `incoming`, `keys`), гарантии релея и список «что доделать до продакшена». Читать первым.
- `server.js` — Express-сайт MINI ID.
  Вход через Яндекс OAuth (`/auth/login`, `/auth/callback`, `/auth/logout`), страница `/profile` для выбора @ника, публичное API `GET /api/users/:username/key`, `GET /api/users/:username` и `GET /api/health`; сессии на cookie. Лезть сюда при правках входа, профиля и публичных эндпоинтов.
- `server.js.bak` — старый ручной бэкап server.js.
  Это почти та же версия, но без эндпоинта `GET /api/users/:username` (проверка существования ника для поиска в мессенджере). Устарел, в git ему не место — историю хранит git; можно удалить.
- `relay.js` — релей-воркер («почтальон»).
  Раз в интервал обходит Диски пользователей, переносит конверты `msg__…` из `outgoing` одного в `incoming` другого, отвечает на `keyreq__…` ключом, синхронизирует `keys/public.json` в БД. Проверяет, что отправитель совпадает с владельцем Диска, и не дублирует сообщения через таблицу `processed`; сюда лезть при ошибках доставки.
- `db.js` — слой доступа к SQLite.
  Выбирает драйвер (`node:sqlite` или `better-sqlite3`), создаёт таблицы `users`, `sessions`, `processed` (режим WAL), даёт функции вроде `upsertUserFromOAuth`, `setUsername`, `createSession`, `userBySession`. Путь к файлу БД можно задать переменной `MINI_DB`; это единственная точка работы с базой.
- `yandex.js` — клиент Яндекс OAuth и REST Яндекс.Диска.
  Строит ссылку авторизации, меняет код на токен, обновляет токены и ходит в `cloud-api.yandex.net` от имени пользователя. Используется server.js и relay.js.
- `config.js` — загрузчик настроек.
  Читает `config.json`, переменные окружения `MINI_CLIENT_ID`, `MINI_CLIENT_SECRET`, `MINI_BASE_URL`, `MINI_PORT`, `MINI_RELAY_INTERVAL` имеют приоритет; задаёт лимит конверта 256 КБ и завершает процесс, если нет ID/секрета OAuth.
- `config.example.json` — шаблон настроек.
  Поля CLIENT_ID, CLIENT_SECRET, BASE_URL, PORT, RELAY_INTERVAL_MS с заглушками вместо значений; копируется в `config.json`.
- `config.json` — рабочий конфиг сервера (копия `config.example.json` с заполненными значениями). В git его держать не нужно — у каждого окружения свой.

- `mini-server.db` — файл базы SQLite с данными сервера.
  Реальные аккаунты, сессии и список обработанных сообщений (в таблице `users` лежат OAuth-токены пользователей). В git ему не место — добавить `*.db` в .gitignore и убрать из индекса.
- `mini-server.db-wal` — журнал записи SQLite (режим WAL).
  Временный файл с ещё не слитыми в основной файл изменениями; без него база может быть неполной. Только для рантайма, в git не нужен.
- `mini-server.db-shm` — служебная разделяемая память SQLite для WAL.
  Пересоздаётся автоматически при открытии базы; в git не нужен.
- `tests/relay.test.js` — тест релея.
  Подменяет `yandex.js` мок-Диском в памяти и БД `:memory:`, проверяет перенос сообщений, анти-спуфинг и идемпотентность. Запуск: `npm test`.
- `tests/smoke-test.js` — смоук-тест клиента без браузера.
  Через jsdom и fake-indexeddb поднимает `index.html` и прогоняет ключевые сценарии; нужны dev-пакеты jsdom и fake-indexeddb.
- `public/style.css` — стили страниц сервера.
  Дизайн-токены MINI для HTML, который отдаёт server.js (вход, профиль); раздаётся по `/static`. Не путать с `css/` клиента.
- `index.html` — единственная страница клиента-PWA.
  Вся разметка мессенджера (чаты, настройки, модалки) и подключение css/js по порядку: storage, crypto, auth, disk, directory, network, modal, settings, messenger, app.
- `manifest.json` — манифест PWA.
  Имя «MINI Messenger», режим standalone, иконки из `assets/icons`; нужен для установки на телефон.
- `sw.js` — Service Worker.
  Кеширует оболочку приложения по файлам и отдаёт `index.html` при офлайн-перезагрузке, чтобы MINI открывался без сети. Бизнес-логики нет; при добавлении файлов клиента их нужно внести в список кеша.
- `js/app.js` — точка входа клиента.
  Инициализирует модули в порядке Storage → Crypto → UI, навигация и регистрация Service Worker.
- `js/storage.js` — единственная точка доступа к IndexedDB (`mini-db`).
  Хранит токен и ключи устройства; другие модули в IndexedDB напрямую не лезут.
- `js/crypto.js` — криптография на WebCrypto.
  ECDH P-256 для ключей устройства, общий секрет → AES-256-GCM для полезной нагрузки; ничего самописного.
- `js/auth.js` — вход через Яндекс без callback.
  Использует `verification_code`: пользователь вручную вставляет полученный токен.
- `js/disk.js` — транспорт через Яндекс.Диск.
  REST-запросы к Диску, папки `MINI/incoming`, `outgoing`, `cache`, `keys`, `config`; в него смотреть, если не уходят или не приходят сообщения.
- `js/directory.js` — каталог пользователей на клиенте.
  Находит @ник и публичный ключ: онлайн напрямую по `/api/users/<ник>` сервера, в режиме белых списков через файл `keyreq__<ник>.json` на Диске.
- `js/network.js` — индикатор сети.
  Три состояния: online, whitelist (доступен только Яндекс), offline; от него зависит выбор «дороги» в directory.js.
- `js/messenger.js` — список чатов, лента и композер (самый большой клиентский файл).
  Сейчас частично работает на демо-данных из дизайн-прототипа, настоящий транспорт подключается через disk.js.
- `js/settings.js` — экран настроек.
  Авторизация по токену, просмотр файлов Диска, отладочный лог.
- `js/modal.js` — модальное окно.
  Открытие/закрытие и список файлов Диска.
- `css/app.css` — базовые стили клиента.
  Токены дизайна, локальный шрифт Caveat, каркас и экран настроек.
- `css/messenger.css` — стили списка чатов, переписки и композера.
- `css/modal.css` — стили модального окна.
- `css/network.css` — стили индикатора сети и тултипа.
- `assets/fonts/caveat-latin.woff2`, `caveat-latin-ext.woff2`, `caveat-cyrillic.woff2`, `caveat-cyrillic-ext.woff2` — локальные файлы шрифта Caveat.
  Подключаются в app.css, чтобы шрифт работал без доступа к Google Fonts (белые списки). Четыре файла описаны одной строкой: это наборы символов одного шрифта.
- `assets/icons/icon.svg` и `assets/icons/icon-maskable.svg` — иконки приложения.
  Обычная и «maskable» (с запасом под круглую обрезку Android) версии; используются в манифесте и `index.html`.
